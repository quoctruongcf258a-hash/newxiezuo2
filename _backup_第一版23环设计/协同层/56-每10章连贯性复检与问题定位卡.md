# 56 · 每 10 章连贯性综合复检 + 问题定位卡

> 本文件由 `scripts/export_newskill.py` 从 apps.json / roster.json 自动生成，请勿就地手改；改配置后重跑脚本。

按期连贯性综合复检（用户最新裁定）：每 10 章触发一次，全员参与，做『近 10 章连贯性』+『全文连贯性』双重检查，输出带优先级的问题清单，由作者裁定是否有必要改动。只复盘、不自动改稿，不阻断日更与已发布正文。位置：入库之后、开始下一章之前；卷末与全书完结另跑完整版。


## 一、为什么需要它

逐章质检管「这一章对不对」，看不见「十章连起来还对不对」。**这是唯一能抓住「十章慢慢漂移」的机制**——设定悄悄变、人物状态断层、伏笔埋多收少、主线悄悄偏离已锁章纲，单章看都没问题，合起来才出问题。

## 二、触发与参与

- **every**：10
- **unit**：章
- **at**：入库之后、开始下一章之前（即 推演下一章 之前）
- **alsoAt**：卷末、全书完结

- 参与：全员 N（每个人既是写手也是盲审官）

## 三、双范围检查

### 近10章连贯性
- [ ] 章间衔接（钩子承接 / 时间衔接 / 场景接续）
- [ ] 人物状态接续（境界 / 伤势 / 关系 / 目标 / 位置）
- [ ] 伏笔埋收状态（近10章埋的埋了没、该收的收了没）
- [ ] 时间线连续（日期 / 季节 / 旅程时长）
- [ ] 设定一致（能力 / 代价 / 势力 / 地理）
- [ ] 情绪与节奏曲线（是否一条平线 / 连续同强度冲突）

### 全文连贯性
- [ ] 主线是否跑偏已锁章纲
- [ ] 人物弧光是否原地打转
- [ ] 设定是否前后漂移
- [ ] 伏笔总账是否失衡（埋多收少）
- [ ] 金手指规则是否越界
- [ ] 卷结构目标是否达成

## 四、输出形式与优先级

- **form**：问题清单（全员汇总，去重后排序）——每条问题必须是『问题定位卡』，不是一句话结论
- **fields**：问题编号、优先级、①问题出在哪、②哪一条出了问题、③正文关键句、④修改建议、影响范围、作者裁定

## 五、★ 问题定位卡（四件套）

问题定位卡（用户硬性要求）：每条问题必须写清「出在哪 / 哪一条 / 正文关键句 / 怎么改」四件套，做到拿着这张卡就能直接跳到正文那一句——不看上下文也知道该改哪、为什么改、怎么改。四件套缺任一，该条问题不成立，退回提出者重写。

| 件 | 字段 | 必须写清 | 格式 | 范例 |
|---|---|---|---|---|
| **①** | **问题出在哪** | 定位到最小可操作单位，逐级写全，不许跳级 | 程序 › 环节 › 卷 › 章 › 六要素段位(始/显/通/动/成/终) › 场景序号 › 段序号 | 写作 › 正文 › 第3卷 › 第57章 › 动 › 场景2 › 第4—7段 |
| **②** | **哪一条出了问题** | 写明命中的具体条目，并引用条目原文或编号 | 标准来源 › 条目编号或原文（命中多条时全部列出） | sixElements 红线「动≠成」（动段只写了动作，没有结果兑现）；platform.chapterSpec「每 500—800 字一个转折点」（本章 1900 字仅 1 处转折，低于下限） |
| **③** | **正文关键句** | 给出能在正文中直接检索到的字串（Ctrl+F 必须搜得到） | 原句（20—40 字）+ 检索词（句中 2—4 个独特词，用 / 分隔） | 原句：「他抬手，剑未出鞘，那人的头已经落了，满地血污他却连眼都没眨。」｜检索词：剑未出鞘 / 头已经落了 / 连眼都没眨 |
| **④** | **修改建议** | 具体到怎么改：改哪句、加什么、删什么、往哪个方向改 | 改法方向 + 改动范围（句/段/场景） + 改后示例（能写就必须写） | 把『动』段第4—7段合并为2段，删去中间3句环境描写，改为「剑未出鞘，人已落」直接给结果；其后补1句代价余韵（手指在抖），作为『终』的引子。改动范围：第4—7段。 |

### 5.1 每件套的硬规则

**① 问题出在哪**
- 严禁只写章号（如『第57章有问题』）或只写程序名；必须落到『段位 + 场景 + 段』这一级，否则无法定位。规划类问题写到环+子项（如 规划 › 世界规则最小集 › 力量体系·代价 第2条）。

**② 哪一条出了问题**
- 必须可对照到标准条目；不得只写『节奏不好』『有点水』『感觉不对』这类无源主观描述。
- 可引用的标准来源：
  - auditDirections（规划八方向，如 五·结构与结局 第5条）
  - sixElements（写作六要素与四条红线，如 红线「动≠成」）
  - writingEnvironment（写作 29 环节，如 结构推进类 18-冲突推进）
  - polishStandard（润色四节子项，如 三·去AI味 13-删总结升华）
  - qcStandard（质检 20 节，如 十二-文风与去AI味回查 第2条）
  - platform（番茄档案，如 chapterSpec「每500—800字一个转折点」/ reviewRedlines 四类低质）

**③ 正文关键句**
- 必须是正文里原样存在的字串。① 缺失类问题（该有没有）：写『缺失点前一句原句』+『应插入的段位』；② 跨多处问题：列出全部关键句；③ 检索词不得取全文高频词（如『他说』『只见』『缓缓』），必须独特到能唯一定位。

**④ 修改建议**
- 不得写『建议优化』『建议加强』『注意一下』这类空话；至少给出改法方向 + 改动范围。

### 5.2 自检（缺件即无效）

- [ ] 四件套（①出在哪 ②哪一条 ③关键句 ④怎么改）缺任一 → 该条问题视为无效，退回提出者重写。
- [ ] ②与③必须对得上：按③的检索词去正文能搜到，且该处确实命中②所述条目。
- [ ] ③的检索词必须唯一可定位；若在正文中搜出多处，说明检索词取得不够独特，需重取。
- [ ] ④必须可执行：拿着④能直接动手，不需要再追问『具体怎么改』。

**去重规则**：全员汇总去重时，以『①位置 + ③关键句』为同一问题的识别键；同一问题被多人提出的合并为一条，提出者并列记录，优先级取最高。

## 七、作者裁定

- **by**：作者
- **rule**：作者拿到的不是一句结论，而是逐条『问题定位卡』：看①知道跳到哪一行，看②知道违反了哪条标准，看③能直接在正文里搜到那句话，看④知道怎么改。逐卡三选一裁定——改（按类型回对应程序返修：表达→润色 / 内容→写作 / 设定→规划）｜不改（记入留档，不阻断更新节奏）｜延后（登记待办，下次复检再议）。
- **note**：AI 只出定位卡与建议，不代替作者决定改不改；已发布正文除非作者明确确认，否则不回改。作者裁定结果回填『作者裁定』字段后归档，作为下一轮成书检验与伏笔状态账的输入。

## 八、复检规则

- 每 10 章必跑一次；卷末与全书完结另跑完整版。
- 复检结果进归档，作为下一轮成书检验与伏笔状态账的输入。
- 复检发现 P0/P1 且作者确认要改的，返修后必须复检。
- 复检不替代逐章质检：逐章质检管『这一章对不对』，复检管『十章连起来对不对、全书还对不对』。

**成本提示**：复检是独立于逐章质检的额外一轮全员窗口操作，每 10 章一次。建议先按 10 章粒度跑，稳定后再考虑加密或放宽。
